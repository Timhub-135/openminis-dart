# OpenMinis → Dart (Flutter) rewrite

A faithful re-architecture of **OpenMinis** (`github.com/OpenMinis/OpenMinis`)
in Dart, targeting **Windows + Android only** (no iOS). The original is a
native iOS (Swift/SwiftUI) + Android (Kotlin/Compose) agentic AI app. This repo
rebuilds its *core agent system* as a single cross-platform Dart codebase, gives
the agent its **Linux shell sandbox via Docker + Alpine on Windows**, and adds
the one thing the iCloud-centric original couldn't do across these two OSes:
**cross-device conversation / history / output synchronization** (Windows ⇄
Android) with deterministic conflict resolution.

> This is a re-architecture of the product's core and a working reference of the
> sync feature. Full feature parity (every OS integration) still needs platform
> native offloads — see [Scope](#scope).

## Linux shell sandbox

The agent's "real Linux shell" (the heart of the original, via iSH on iOS /
PRoot on Android) is re-created per platform:

- `sandbox/sandbox.dart` — platform-agnostic `Sandbox` interface (`run`, `exec`,
  `readFile`, `writeFile`…).
- `sandbox/windows_docker_sandbox.dart` — **Windows: DockerAlpineSandbox**:
  `docker run` `alpine:<tag>` once, detached, with the app data dir bind-mounted
  at `/var/minis/`; then `docker exec` for commands and stdin/file transfer.
- `sandbox/android_termux_sandbox.dart` — **Android: runs commands inside the
  installed Termux shell** (no root / PRoot / Docker needed), bridging results
  through a shared directory + the `com.termux.RUN_COMMAND` broadcast.
- `sandbox/sandbox_factory.dart` — picks the right implementation per platform.
- `sandbox/sandbox_tool.dart` — exposes the sandbox to the agent as
  `linux_sh` / `sandbox_read` / `sandbox_write` tools.

### Windows — Docker Alpine

```sh
docker run -d --name openminis-sandbox -v /path/to/data:/var/minis --entrypoint /bin/sh alpine:3.21 -c "sleep infinity"
```
The app does this for you on first launch (see `DockerAlpineSandbox.start()`).

### Android — Termux (when already installed)

This app doesn't ship its own Linux sandbox on Android; it **lets the agent use
Termux**, which is a real Linux environment already on the phone. Because an
Android broadcast has no return value, commands run through a small file bridge:

1. App writes `cmd_<id>.txt` into a **shared** dir (e.g. `/sdcard/Download/.openminis`,
   readable by both the app and Termux).
2. App fires `com.termux.RUN_COMMAND` → Termux runs an installed `run.sh`
   helper that sources the command in a subshell, captures stdout/stderr + exit
   code, and writes `result_<id>.json`.
3. App polls for the result JSON, parses it, and returns a `SandboxResult`.

**Device setup (one-time):**
- Install Termux; enable **Allow external apps** (`termux-setup-storage`, and in
  Termux long-press → More → Allow external apps).
- Grant the app storage permission so both sides share the bridge dir.

### Faithful details kept in the port
- **TokenUsage folds with `max()`** not `+=`, so providers that stream
  cumulative usage don't inflate totals quadratically.
- **Adaptive thinking flush** (`thinkingFlushTiers` 0.3s → 0.6s → 1.0s) so a
  long streaming "thinking" block doesn't repaint per token.
- **SSE parser** handles `data:` multi-line, comments, CRLF, chunk splits, and
  trailing unterminated frames.
- **Internal bridge / leak guard** on messages that must never render.
- **minis://** URL derivation with percent-encoding and on-disk resolution.

## The new feature: cross-platform sync  (Windows ⇄ Android)

The original syncs through **iCloud**, which doesn't span Windows/Android. This
rewrite ships `sync/sync_engine.dart`:

- **Revision high-water marks** per session compute a *minimal delta* (only what
  the peer is missing is transferred).
- **CausalId ordering** (`(deviceId, seq)`, totally ordered, deterministic) makes
  conflict resolution convergent on both replicas with no central authority.
- **Tombstones** propagate deletions, so "delete on this device" deletes on the other.
- Two transports (@ `lib/src/sync/lan_transport.dart`):
  - **LAN** — advertise/pull/push over plain JSON HTTP on `:8741`. Both devices
    on the same network reconcile every few seconds.
  - **Hub/relay** — same protocol against a self-hosted relay (optionally with a
    password for AES-GCM at rest, opaque to the relay).

A typical pair-up:

```sh
# Windows — host the hub and bind the sync transport
flutter run -d windows --dart-define=SYNC_PEER=192.168.1.20

# Android — point at the Windows peer
flutter run -d android --dart-define=SYNC_PEER=192.168.1.20
```

Both devices then share existing conversations, new turns, edits and deletions.

## Building

Prereqs: Flutter SDK (`≥3.22`), for Android the NDK as usual, for Windows
Visual Studio (Desktop C++ workload). `dart_lib` needs only the Dart SDK.

```sh
# 1) platform runners (Windows + Android) — generates missing stub dirs
flutter create --platforms=windows,android --org com.openminis .

# 2) wire in the core + app shell
flutter pub get

# 3) run
flutter run -d windows
flutter run -d android
```

## LAN web server (run inside OpenMinis, no Flutter)

The Dart rewrite also ships as a **pure-`dart:io` web service** — run it *booted
inside an OpenMinis host* and it binds **0.0.0.0**, so any phone/desktop browser
on the local network reaches the same agent:

```sh
cd server
dart pub get
dart run bin/lan_server.dart 8741     # bind all interfaces on :8741
```

- `GET /` — minimal chat UI (self-contained HTML).
- `POST /api/chat {text, sessionId?}` — runs the agent loop, returns the reply.
- `GET /api/sessions` `GET /api/session/<id>/messages` `GET /api/health`
- If no provider API key is configured, the default `EchoLlm` answers
  deterministically so the service is demonstrably alive with no model network.

Tested end-to-end in this repo (server started on `:8741`; REST + the
in-browser chat flow both driven and verified).

To attach a real provider, inject an `LlmClient` (see `AgentLoop`). API keys go
through `SecretResolver` (never echoed to logs).

## Scope

Targets **Windows + Android only** (no iOS). This rewrite delivers the **core
agent runtime** (models, stores, tool loop, provider streaming, memory/skills),
a working **Linux shell sandbox** (Docker+Alpine on Windows; Termux on Android),
and the **sync engine**, all tested. Deep per-OS integrations (Health/HomeKit/
Shizuku etc.) stay as extra `Tool`s per platform — the `ToolRegistry` and
`AgentLoop` are shaped so those drop in without touching the core.
